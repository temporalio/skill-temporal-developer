# Rust SDK Testing

## Overview

Rust Temporal tests should prove both normal Rust behavior and Temporal behavior. Unit tests are useful for pure logic and Activities, but Workflows need an integration or replay surface because determinism depends on Event History.

## Local Smoke Test

Use the dev server for a first end-to-end check:

```bash
temporal server start-dev
```

In another terminal, run a Worker. In a third terminal, run a starter/client that starts the Workflow and waits for the result.

The upstream Rust SDK examples follow this shape from `crates/sdk/`:

```bash
cargo run --features examples --example hello-world-worker
cargo run --features examples --example hello-world-starter
```

For app repos, create equivalent commands that start the Worker and execute a representative Workflow.

## Activity Unit Tests

Activities are normal async Rust functions generated by macros. Keep business logic easy to test outside Temporal by extracting pure helpers.

For simple Activities, direct invocation can be used in compile or unit tests when you can provide an `ActivityContext`. Otherwise, test the inner helper and cover the Activity through integration tests.

```rust
#[tokio::test]
async fn formats_greeting() {
    assert_eq!(format_greeting("Temporal"), "Hello, Temporal!");
}
```

## Workflow Registration Tests

At minimum, assert that Workers can register Workflow and Activity types:

```rust
#[test]
fn registers_worker_types() {
    let _ = WorkerOptions::new("task-q")
        .register_workflow::<MyWorkflow>()
        .unwrap()
        .register_activities(MyActivities)
        .build();
}
```

Registration tests catch duplicate Workflow types, missing macro wiring, and some compile-time API drift.

## Integration Tests

A meaningful Workflow integration test should:

1. Start or connect to a Temporal dev server.
2. Start a Worker registered with the Workflow and Activity types under test.
3. Start the Workflow with a unique Workflow ID.
4. Wait for the result or assert the expected failure.
5. Shut down the Worker cleanly.

Use stable IDs and timeouts so failures are diagnosable. Avoid sleeps when the test can wait on Workflow results, channels, notifications, or Temporal handles.

## Testing Signals, Queries, and Updates

For message handlers:

- Start a Workflow that waits on state, such as `ctx.wait_condition(...)`.
- Send a Signal or Update from the Client.
- Query the Workflow state.
- Assert the final Workflow result.

This catches handler registration, payload compatibility, and state mutation bugs.

## Testing Cancellation

For cancellation:

- Schedule a cancellable Activity with a Heartbeat Timeout.
- Cancel the Workflow from the Client.
- Assert that cleanup ran or the expected cancellation result was returned.
- Verify long-running Activities check `ctx.is_cancelled()` and heartbeat.

## Testing Continue-As-New

Make Continue-As-New testable by passing a small test limit in Workflow input. Keep all state needed by the next run in the Continue-As-New input.

```rust
ctx.continue_as_new(
    &(current_iteration + 1, max_iterations),
    ContinueAsNewOptions::default(),
)?;
```

Assert that the final result is produced after the expected number of runs.

## Replay and Versioning Tests

Replay is the strongest check for Workflow code changes. If your project stores production or fixture histories, replay them before deploying a Workflow change. If replay tooling is not already wired for your Rust app, use patching for changes that affect Command order and add an integration test that exercises both old and new branches where practical.

## Upstream SDK Repo Commands

When working in `temporalio/sdk-rust`, use the repo command surface:

```bash
cargo build
cargo test
cargo integ-test
cargo lint
cargo +nightly fmt --all
```

Integration tests can start an ephemeral server by default. They can also use an external server with `cargo integ-test -s external`.

## Best Practices

1. Unit-test pure Rust logic separately from Temporal.
2. Smoke-test the Worker plus Client path against a dev server.
3. Test Signals, Queries, Updates, cancellation, and Continue-As-New through handles.
4. Avoid test sleeps when a deterministic wait or handle result exists.
5. For deployed Workflow changes, prefer replay tests plus patching.
